# 提案: 魚拓（Wayback）の登録がボトルネックになっている件

- 作成: 2026-10-31（測定は同日 18:07 JST まで。base は main の `f1efb90a`）
- 状態: **第1段（§5）を 2026-10-31 に実装した**（同じ PR・作法は handoff §4「`pipeline:archive` の実行の作法」）。第2段・第3段は §6 の判断待ち
- 対象: `pipeline/archive.ts`・`data/archives.json`・収録の巡の手順（loop.md・`/ingest-source`）

## 1. 結論

**ボトルネックになっている。** ただし「1件が遅い」よりも、次の2つが効いている。

1. **積み残しが増え続けている。** Wayback の写し（②）が無い資料は、2026-09-26 の 224件から、10-31 には **1,089件**に増えた（全 4,715件の 23.1%）。そのうち 1,056件は「要許可」の資料。要許可の資料は自サーバーで配信しない（③が無い）ので、発行元が消したら、読者がたどれる写しは②しか無い。
2. **SPN（Save Page Now）が止まると、収録の巡が止まるか、持ち越しが溜まる。** 匿名の SPN は、確かめられただけで8月下旬から6回止まっている。10-31 だけでも2回止まった（朝と夕方）。止まっている間の「未確認」は、遅れているだけなのか、拒まれているのかを `archive.ts` が区別しない。失敗を記録もしないので、未確認率を台帳から数えられない。

推奨は §5 のとおり、3段階で進めること。

- **第1段**（判断はほぼ不要・小さい）: 止まったら打ち切る、待つ時間に上限を付ける、試行を記録する、ロックファイルを置く、HTML の古い捕捉を使い回さない。
- **第2段**（ユーザーが archive.org のアカウントとキーを用意する）: 認証つきの SPN2 API に切り替える。登録要求だけ投げて、結果は後でまとめて確かめる。
- **第3段**（ユーザーが運用の方針を決める）: 巡の中では登録要求を投げるだけにして、台帳への記録はマージ後の単一の定期ジョブに集める。

### 2-4. 未確認の割合

**台帳からは数えられない。** `archive.ts` は「✗ 未確認」を画面に出すだけで、どこにも残さない（`pipeline/archive.ts:449-452`）。巡の記録に残っている数は次のとおり。

| 巡 | 記録 |
| --- | --- |
| 第87〜91巡（10-22） | 「すべて未登録」（31・8・16ソースなど。接続できず） |
| 第97巡（10-28） | 63ソース中60件が登録・照合済み。熊取町の年度ページ2件が未確認（翌巡で登録） |
| 第99巡（10-31・#422） | 原本59ファイルすべて登録・一致 |
| 宮城・広島・山口（#420・10-31 朝） | 12 URL を持ち越し（save が 520） |
| 熊本・鹿児島・石川・和歌山（#421・10-31 朝） | 38 URL（15団体）を持ち越し（save が 520） |
| 福島・岩手・奈良・岡山（#423・10-31 昼） | 持ち越し50 URL を取り直し、5 URL が3回続けて未確認（10%） |
| 香川〜秋田（#425）・第100巡（#426）（10-31 夕） | 起動元セッションの申し送りでは「夕方に全件未確認・`--force` の取り直しも全滅」 |

失敗の型は、記録から少なくとも4つに分かれる。いまはどれも同じ「未確認」と表示される。

1. **SPN 全体の停止**（520・Temporarily Offline・接続拒否）。待つしかない。
2. **受け付けたが実体化が遅い**。CDX に載るまで数十分から13時間かかった実例がある（data-sources §9b の 2026-08-13 の項）。`archive.ts` は約1分しか待たない（`POLL_TRIES` 10回×6秒）ので「未確認」になり、次の実行で CDX から拾われる。
3. **発行元がクローラを弾いている**（東村山。メモリ publisher-may-block-wayback）。待っても直らない。
4. **429（回数の上限）**。6秒間隔では 429、60秒間隔では通った日と、120秒間隔でもほぼ全件 429 だった日がある（§9b の 2026-08-12・08-13 の項）。CDX も同じ時期に 429・504 を返した。

### 2-5. 並行のセッションとの取り合い

- 10-31 17:47〜17:48 JST、**別々のワークツリーの2セッション**（香川〜秋田・第100巡）が同時に archive を回していた。2本の捕捉時刻は交互に並び、08:47Z の1分間に4件取れていた。公開文書にある匿名の上限は毎分3件。その約20分後に 520 になった。**因果は未確認。**
- 匿名の上限は IP ごとに数えられる（公開文書の記載）。**同じ Mac から回すセッションは、いくつあっても1つの枠を分け合っている。**
- 公開文書の「匿名は1日200件」を超えた日もある（10-21 UTC に新規の捕捉が少なくとも321件）。【解釈】文書の数字が、そのまま効いている上限とは言えない。

「3層」の列は、エビデンス3層コピーの原則（CLAUDE.md・data-strategy.md §5）を壊さないかを見たもの。

| 案 | 中身 | 効果 | コスト | リスク | 3層 | 人が決めること |
| --- | --- | --- | --- | --- | --- | --- |
| **A. 認証つきの SPN2 API** | `POST https://web.archive.org/save`（`Authorization: LOW <access>:<secret>`・`Accept: application/json`）。`job_id` を受け取り、`/save/status/<job_id>` で結果を見る | 公開文書では、上限が毎分3件・1日200件から、**毎分7件・1日3万件**に上がる（数字は文書の記載で、実効値は未確認）。結果が `error:blocked-url`・`error:too-many-requests` などに分かれるので、§2-4 の型1〜4を区別できる。`if_not_archived_within` で「最近の捕捉があれば取らない」を IA 側に任せられる | 実装は1セッション程度。キーは `.env`（gitignore 済み）と GitHub の Secrets に置く | IA 全体が止まる日（09-10・10-31 夕の 520）は直らない。認証つきの待ち行列も混む（10-31 18:07 に 26,728件） | 変わらない（②の中身は同じ） | 誰の名義でアカウントを作るか。キーの置き場所。archive.org の利用規約への同意 |

## 5. 推奨

### 第1段: すぐ入れられるもの（E・G・H・I）

判断がほぼ要らず、`archive.ts` と derive の入口だけで済む。

1. fetch にタイムアウトを付ける。520 が続いたら打ち切って「SPN 停止」と報告する。要求の間隔は、同じマシンのプロセス全部で共有する（E）。
2. ロックファイルを置き、derive はそれを見たら止まる。台帳は一時ファイルに書いてから入れ替える（G）。
3. 試行の結果を型つきで残す（H）。
4. HTML は、raw の取得日より古い捕捉を使い回さない（I）。

**効果**: 止まっている日に巡が全件の試行で時間を使わなくなり、すぐ「止まっている」と分かる。§3 の 2・3・4・7・8・9 が無くなる。**積み残しの量は減らない**（枠そのものは同じ）。

### 第2段: 枠を広げる（A＋B・ユーザーの判断が要る）

認証つきの SPN2 API に切り替え、登録要求と結果の確認を分ける。

**効果**: 公開文書の数字どおりなら、1日の枠は 200件から 3万件に上がる。そうなれば 1,089件の積み残し（約2,000 URL）は、【試算】毎分7件で約5時間になる。止まった理由も分かれる。**IA 全体の停止は直らない。**

### 第3段: 巡から外す（B＋D・ユーザーの判断が要る）

**巡の中では登録要求を投げるだけ**（取得の直後に。版が変わる前に捕捉させるため）にして、**台帳への記録・照合・derive はマージ後の1本の定期ジョブにまとめる**。

- 捕捉は取得の直後なので、上書き型の URL の版のずれは今と変わらない。②が台帳に載るのは数時間後になる。
- 台帳を書くのが1か所になるので、**C（台帳の分割）は要らなくなる**。巡の中で台帳を書き続ける運用を残すなら、代わりに C を入れる。
- 定期ジョブは、積み残し（§2-1）の解消と、§2-4 の型2（遅れて実体化したもの）の拾い直しも兼ねる。

**3層への影響**: ①raw と③配信は今のまま。②は「取得の直後に捕捉を頼み、記録はマージ後」になる。data-strategy §5 の「新資料は取得（①）したら即座に② Wayback 登録」は、「即座に登録を要求し、記録と照合は定期ジョブで」に書き換える。**要許可の1,056件は②が唯一の公開された写し**なので、第3段より前に、第2段で積み残しを片付けるのがよい。

### 入れないほうがよいもの

- **archive.today**: sha の照合ができず、CAPTCHA を越えないと登録できない。②の役目を果たせない。
- **C を単独で入れること**: 行が消えるのは防げるが、SPN の枠の取り合い（ボトルネックの本体）は直らない。移し替えの PR が大きく、並行の巡を止める必要がある。

## 6. ユーザーが決めること

1. **第1段を入れてよいか**（判断の要らない小さな改修。1つの PR）。
2. **archive.org のアカウントを作るか**（第2段）。作るなら次も決める。
   - 名義（個人か、合同会社 哲學舎か）とメールアドレス。
   - S3 形式のキー（`https://archive.org/account/s3.php` で発行）の置き場所。手元の `.env`（gitignore 済み）だけか、GitHub の Secrets にも置くか。
   - **アカウントの作成・利用規約への同意・キーの発行と入力は、ユーザーが自分で行う**（エージェントは代行しない）。キーはチャットに貼らず、`.env` に直接書く。
3. **巡の中の登録を「要求だけ」にしてよいか**（第3段）。data-strategy §5 の「即座に登録」を書き換えることになる。
4. **定期ジョブを GitHub Actions に置くか、手元の1セッションで回すか**。Actions なら、ボットが出す PR を誰がどの条件でマージするか（CI 緑で自動か、人が見るか）。
5. **WARP の捕捉を②として数えるか**（案 F。Wayback に無い資料の補完）。

## 7. 調べ方（再現の手順）

- 積み残し: `public/coverage.json` の `summary`（`sourceCount − archivedCount`）。内訳は `entities[*].sources` の `archived` と `files[*].fetchedAt`、台帳の行の有無で分けた。
- 所要・停止の時期: 台帳の `waybackTimestamp` と `checkedAt` の差が3時間以内の行を新規の捕捉とみなし、時刻を並べた。10-31 の分は、作業中の5つのワークツリーの台帳を**読むだけ**で合わせた（書き換えていない）。
- SPN の状態: 18:07 JST に `ps` で archive が0本であることを確かめてから、example.com の1件で save・availability・cdx・replay と `/save/status/system` を叩いた（handoff §4 の4本の切り分けと同じ）。
- SPN2 の上限・パラメータ: Internet Archive が公開している「Save Page Now 2 Public API Docs」（Google ドキュメント）。文書の中でも数字が食い違う箇所がある（1日の容量が 500MB と 2GB、取得時間の上限が45秒と2分）。**実効値はどれも未確認。**
